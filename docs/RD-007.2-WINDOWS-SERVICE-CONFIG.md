# RD-007.2 — Serviço e configuração Windows

**Status: concluída localmente. Beta 2 não publicada. Teste em máquina limpa pendente.**

## Problema confirmado

O fluxo anterior encerrava a instalação no sucesso de `--silent-install` e executava
`rustdesk.exe --config <configuração>` sem privilégio administrativo. Além disso,
exit code zero era tratado como `Applied` e podia chegar à tela de sucesso sem uma
releitura independente dos campos.

Em uma instalação nova isso permitia três estados incorretos: serviço ausente,
configuração não persistida e falso positivo de sucesso. A correção considera o
RustDesk operacional somente quando o serviço existe, está `Running` e os valores
reais correspondem à configuração Technolife.

## Confirmação no RustDesk 1.4.9

O código oficial da versão 1.4.9 confirma:

- `--install-service` chama a instalação do serviço Windows;
- o nome padrão usado para criar, iniciar e consultar o serviço é `RustDesk`;
- `--config` exige uma instalação existente e privilégio administrativo;
- os campos importados são `key`, `custom-rendezvous-server`, `api-server` e
  `relay-server`;
- `--option <nome>` lê as opções persistidas por IPC e também exige privilégio
  administrativo.

## Fluxo implementado

```text
duplo clique
→ uma confirmação UAC
→ detectar RustDesk
→ baixar, validar e instalar quando ausente
→ redetectar executável
→ consultar serviço RustDesk
→ executar --install-service quando ausente
→ aguardar o serviço aparecer
→ garantir Running
→ executar --config como administrador
→ reler opções com --option
→ comparar ID Server, Relay Server e chave
→ confirmar serviço ainda Running
→ Verified ou falha
```

O Core representa o andamento com `Checking`, `Downloading`, `Installing`,
`StartingService`, `Configuring`, `Verifying`, `Completed` e `Failed`. A GUI traduz
os novos estágios para “Ativando acesso remoto...”, “Configurando acesso remoto...”
e “Validando configuração...”.

## Serviço Windows

`WindowsRustDeskServiceManager` centraliza o nome `RustDesk`. A consulta e o controle
usam `SystemWindowsServiceController`, baseado em
`System.ServiceProcess.ServiceController`; o produto não chama PowerShell nem
`cmd.exe`.

Quando o serviço não existe, o gerenciador executa o binário detectado com o argumento
separado `--install-service` e elevação obrigatória. Em seguida, faz até dez consultas
com intervalo de um segundo. Serviço parado recebe `Start`; serviço pausado recebe
`Continue`; estados pendentes são acompanhados. O fluxo falha e não chama `--config`
se o estado `Running` não for alcançado.

## Elevação única e processos

`Program` detecta se a GUI já está elevada. Quando não está, relança o próprio EXE
uma única vez com `runas`, aguarda o filho e exibe mensagem amigável se o consentimento
for recusado. A janela principal só é aberta no processo elevado; o UAC nunca é
automatizado.

`WindowsProcessElevationContext` concentra a consulta a `WindowsIdentity`.
`SystemProcessRunner` usa `runas` apenas quando uma requisição administrativa parte de
um processo não elevado. Se o token atual já é administrativo, o processo filho é
iniciado diretamente, herda esse token e mantém captura de stdout, stderr e exit
code. Argumentos continuam separados em `ProcessStartInfo.ArgumentList`.

## Configuração e validação real

`WindowsRustDeskConfigurator` marca `--config` como operação administrativa e nunca
inclui a string exportada nos logs. Exit code zero significa apenas `Applied`.

`WindowsRustDeskOptionReader` relê, pela CLI oficial, exatamente:

| Opção RustDesk | Valor esperado |
|---|---|
| `custom-rendezvous-server` | `remoto.technolife.net.br` |
| `relay-server` | `remoto.technolife.net.br` |
| `key` | chave pública documentada em `SERVER-CONFIG.md` |

`api-server` não é validado porque não faz parte da configuração esperada. O
`WindowsRustDeskValidator` só retorna `Verified` quando os três valores correspondem
exatamente e o serviço continua `Running`. Qualquer divergência retorna
`ValidationFailed`, inclusive quando `--config` terminou com zero.

A implementação oficial aplica e consulta opções via IPC. Por isso não há leitura ou
escrita direta de TOML nem reinício arbitrário do serviço. O validator apenas repete
a leitura por polling curto para acomodar a persistência.

## Testes

Os testes automatizados cobrem:

- instalação nova seguida de serviço, configuração e validação;
- serviço ausente, parado, pausado e incapaz de iniciar;
- criação idempotente do serviço;
- elevação recusada;
- processo já elevado sem segundo UAC e com captura de saída;
- leitura das três opções;
- configuração divergente substituída e validada;
- falso positivo: `--config` retorna zero, uma opção permanece errada e o resultado é
  `ValidationFailed`, nunca `Completed`;
- execução repetida sem reinstalação nem recriação do serviço.

Na validação local, os 119 testes passaram.

## Teste real por duplo clique

O artefato local foi aberto pelo Explorer. O usuário confirmou um único UAC; não foi
necessário abrir ou desbloquear as configurações de rede nem clicar em “Iniciar
serviço”. O configurador mostrou “Configuração concluída com sucesso”. O log registrou
`Applied`, releitura independente e `Verified`; o serviço `RustDesk` ficou `Running`
com inicialização automática.

Na inspeção posterior, a tela principal do RustDesk mostrou `Pronto`, um ID local e,
em Configurações > Geral, a ação disponível era `Parar`, confirmando o serviço ativo.
Configurações > Rede exibiu `Desbloquear configurações de rede`; esse controle não foi
acionado. Portanto, os campos não foram expostos visualmente, e sua confirmação foi
feita pela leitura oficial `--option` antes de a GUI permitir sucesso.
